# KV-cache prefix replay (`[workload.kv_replay]`)

- **Opened:** 2026-10-12
- **Status:** OPEN — built and tested locally on mio (macOS) against an
  in-process RESP server. Not yet run against a real server, on io_uring, at
  more than two connections, or with a trace larger than three requests.
- **Commits:** f8817b7, 81a086b, 2f11602, cf0c163, 40e00c0, c2228b0,
  2f15a80, 8f0fa68, 67e635e, d2def90, 861b347, 1eb8df0, a7c8fd2, ad56d99,
  0fbaa49, 79e8bfd, 07e6617, and the commit that updated this list, on
  `feat/kv-replay`.

## Problem

A KV-cache workload from LLM serving uses a cache server as a prefix store:
for each inference request the engine looks up the KV objects of the prompt's
full chunks, loads the cached prefix, and stores the rest. What matters is
prompt tokens served from the cache against tokens computed, and how long the
lookups and loads take. cachecannon's synthetic keyspace cannot produce that
access pattern: the keys, sizes and their dependence on earlier requests come
from the prompts. kvtrace (pelikan-io/cachesim `crates/kvtrace`) defines a
request-level trace and the mapping from a request to its objects; this replays
such a trace.

This is not the key-sequence replay scoped in `2026-09-10-trace-replay.md`,
which leaves timing-faithful replay to a separate effort because saturation
search needs cachecannon to control the rate. Here
the trace's timing is part of the workload (request arrival drives which
prefixes are still cached), so open loop at the trace's timestamps is the
default and closed loop is the alternative.

## Decisions

- **One trace request per connection, three dependent steps.** EXISTS of every
  object in one pipeline, then GETs of the hit prefix, then SETs, the GETs and
  SETs at most `pipeline_depth` in flight. `drive_resp_workload`'s fire loop
  assumes independent requests, so `src/kvreplay.rs` has its own loop and the
  RESP connection task chooses between them. ringline-redis has no
  `fire_exists`; its `Pipeline` sends every command in one send and returns
  replies in order, which is what the lookup needs, at the cost of no
  per-EXISTS latency.
- **One timer per worker for the schedule.** A dispatcher task per worker, the
  shape of the rate-limit `TokenDispatcher`, hands requests to idle connections
  and sleeps until each is due. A per-connection sleep would be one timer per
  request per connection (CLAUDE.md, "Price any per-request timer").
- **Store from the lookup's prefix.** LMCache records the lookup result as
  saved and skips that many tokens when storing
  (`vllm_v1_adapter.py:193,247,326`), so an object found by EXISTS and then
  missing at GET is not rewritten by that request.
- **Hybrid models rejected.** kvtrace's hybrid geometry is an approximation;
  replaying it would report token counts for a layout LMCache does not use.
- **Replay clock.** Starts with warmup when there is one, otherwise at the
  Running transition after the baselines. Started at the warmup phase with
  `warmup = "0s"`, a short trace finished before the runner's 100 ms loop
  took its baselines and recorded nothing.

## Verified locally (macOS, mio, debug build)

- `tests/kv_replay.rs` (one binary, each test in its own child process):
  cold cache and full-prompt repeat (63 of 64 tokens cached), shared prefix,
  a gap under each write rule, `tp = 2` minimum over ranks, MLA rank 0 only,
  hybrid rejection, GET nil (at the second chunk and at the first), open
  loop on two connections with one SET reply held 300 ms (lookups 180-260 ms
  apart, due 200 ms apart), a 0-token prompt with chunks, a connection the
  server closes while it is idle, every connection closed at once, a
  handed-back request ahead of a later one, and reconnects that are refused
  or closed at once. Each was seen to fail with the
  behaviour it covers broken; the commit messages name the mutations
  (2f11602, then 2f15a80 after the tests moved into one binary, and each
  fix commit for its own test).
- Defects an adversarial review of 8f0fa68 found, each reproduced before
  the fix: a 0-token prompt with chunks underflowed `new_tokens` (the debug
  run hung until `duration` with 1 of 2 rows; 67e635e); the per-1k load
  count included loads without cached tokens (d2def90); a connection the
  server closed while idle failed the next request and counted it as a
  send-pool failure, because ringline refuses a send on a closed connection
  with `NotConnected` (861b347, which said no request was lost; the second
  review showed that held only for one closed connection, see below); the
  send-pool clamp at `u16::MAX` slots was
  silent (a7c8fd2); `pipeline_depth = 0` was accepted (ad56d99).
- Defects the second review (of 79e8bfd) found, each reproduced, fixed in
  07e6617: a request handed to one closed connection used up its retry, so
  an idle timeout closing every connection at once still lost it (3
  connections: 1 of 2 rows); a handed-back request waited while the
  dispatcher slept until a later request was due (2.4 s, and it ran after
  that later request); a handed-back request with no connection able to
  reconnect kept the run alive until `duration`. Limits that remain: a
  request found on closed connections is handed back at most once per
  connection on its worker, and once after a sent lookup; it is failed when
  none of its worker's connections is connected and a reconnect has failed.
  The wake on hand-back is not distinguished by a test from the
  dispatcher's 50 ms sleep cap.
- In the first open-loop run the first two lookups reached the server 165 ms
  apart instead of 200 ms: the dispatcher polled for the replay clock every
  50 ms, so the first request started late. It now polls every 1 ms until the
  replay starts.

## Not verified

- io_uring, a real server, and large objects (tens of MiB per chunk, sent
  zero-copy). The send pool is sized for one connection's largest EXISTS
  pipeline (`SendLoad::lookup_bytes`), which is computed, not measured.
- Generator cost at high connection counts. The dispatcher and the untimed
  waits follow the existing pattern; nothing here was profiled.
- Schedule lag under load: the only measurement is three requests on two
  connections.

## Open questions

- With `tp > 1` all ranks' operations share one connection, so lookup, load
  and store times are those of one client doing every rank's work. The
  engine's ranks have their own connections. Whether to spread ranks over
  connections depends on which time the reader needs.
- The trace is held in memory. A production-length trace may need streaming
  from the Parquet reader, which also needs the largest request (for the send
  pool) without a full pass.
- vLLM's own GPU prefix cache and LMCache's local CPU tier are not
  modelled: every request is looked up on the server.
- The replay matches LMCache's `resp://` and `valkey://` connectors in keys
  and operations per object, not in concurrency, and does not match
  `redis://`, which stores two keys per object and looks up one key at a
  time (`docs/guide.md`, "Which LMCache connector this matches"). A
  `redis://` shape (two keys, sequential lookup stopping at the first miss,
  two GETs and two SETs per object) would be a separate option.
